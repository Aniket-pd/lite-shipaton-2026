# Lite WebKit implementation notes

Verified before implementation against Xcode 26.3’s **iPhoneOS 26.2 public WebKit headers** and Apple’s online documentation on September 18, 2026. Lite’s deployment target is iOS 17.0. No private selectors, KVC settings, production JavaScript injection, custom user agents, cookie copying, or browser security bypasses are used. A DEBUG-only local page is enabled by two explicit UI-test arguments for file/popup/dialog regression tests.

## Browser layout and website appearance

The saved-app browser reserves one compact bottom control row, with no native top navigation bar. A deliberate downward pan collapses the row into a domain pill; upward pans and tapping the pill expand it. Both states keep at least 44-point touch targets. SwiftUI safe-area insets resize the website viewport, so fixed website controls remain above the native row on iOS 17 and later. The browser does not inject `viewport-fit=cover`, change website CSS, replace WebKit's scroll delegate, or place browser controls over website buttons.

`WebPage` observes public, KVO-compliant `WKWebView.underPageBackgroundColor` (iOS 15+) and uses it for the surrounding native background and scroll-view bounce color. It does not assign `underPageBackgroundColor`, which would override WebKit's automatic color tracking. [Apple API documentation](https://developer.apple.com/documentation/webkit/wkwebview/underpagebackgroundcolor). Website `theme-color` may be an unrelated brand accent, so it does not override the rendered background. This is an HTML/body background signal, not separate pixel sampling of each header, footer, gradient, or video frame.

Native contrast follows the resolved page color. The website's original light/dark preference is captured outside the browser presentation and explicitly applied to its web view, preventing native chrome appearance changes from feeding back into `prefers-color-scheme`. The palette composites transparent colors against the user's system background before selecting readable native text.

Scroll detection observes the existing pan recognizer without taking over scrolling or back gestures. It ignores horizontal gestures, bounce, short documents, and small direction changes. Layout-driven offset changes do not trigger collapse. Controls stay expanded for keyboard entry, popup decisions, loading/errors, downloads, VoiceOver, and accessibility text sizes. Accessibility sizes place website identity on a separate row; Reduce Motion disables the resizing animation and Reduce Transparency uses an opaque control surface. Return controls remain explicit for approved popups and replacement navigation without a Back entry. More also retains Return to previous page whenever recovery is available, including replacement navigation where Back would skip the replaced page.

## Account isolation

`WebSession` obtains a persistent store using the **saved Lite App data-store UUID**, attaches it to `WKWebViewConfiguration`, then creates the root web view. `WebProfileStore` retains one data-store object per UUID for the process lifetime, without retaining web views. Reopening an entry reuses that account’s profile; after process restart, its saved identifier reconstructs the persistent profile. It never selects `.default()` or `.nonPersistent()`. Two entries for the same website have separate identifiers, so WebKit owns their cookies, cache, local storage, IndexedDB, and other website data independently.

Rapid close/reopen tests exposed a cookie-lifetime race when the last store reference was discarded and immediately recreated. A data-store destructor asynchronously removes its networking session; public cookie-setting completion does not guarantee disk flush. Retaining the per-UUID store avoids unnecessary network-session churn. Stores for different Lite Apps remain distinct. There is no private flush call, artificial delay, or cookie copying.

A website-created child uses the exact configuration supplied by WebKit, with this session’s data store explicitly attached before initialization. WebKit loads the child’s original navigation, preserving POST requests and opener relationships. The opener remains mounted underneath the child. There can be one root and at most three child windows. Closing a child does not remove profile data.

Before deleting a profile, release every `WKWebView` using it and remove only its UUID from `WebProfileStore`; Apple documents that removal can fail while a view still owns that store. The app’s deletion flow manages profile removal separately from the browser UI. If WebKit still considers it in use, the durable deletion receipt allows cleanup on a later attempt.

Simulator validation exposed a WebKit crash when profile removal was the first WebKit operation in the process (create an entry, delete it without opening it). The deletion service calls `WebProfileStore.prepareForRemoval` to initialize a public `WKWebViewConfiguration` once if necessary, without creating a web view, reading its lazy default store, or creating an identified profile. [The configuration initializer](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKWebViewConfiguration.mm) constructs a page configuration whose [base API object initializes WebKit](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/Shared/API/APIObject.cpp). [The website-store getter is lazy](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/APIPageConfiguration.cpp). [Store removal](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/WebsiteData/Cocoa/WebsiteDataStoreCocoa.mm) dispatches onto WebKit’s main run loop without initializing it itself.

Cleanup releases the chosen cached profile before removal. It deliberately does not reconstruct that identifier, because [identified-store construction schedules asynchronous directory creation](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/WebsiteData/WebsiteDataStore.cpp), which can race deletion and recreate its directory. These are implementation observations supported by runtime tests, not extra API contracts; Lite invokes only documented public APIs.

## Navigation and recovery

Creation accepts HTTPS website URLs (bare domains are normalized to HTTPS). HTTP(S) links encountered inside a website stay in the current isolated profile, including links to another domain. The full current host remains visible; tapping it shows the URL and connection state. Apple’s default ATS and TLS certificate validation remain active, so insecure HTTP connections may be rejected. Requests with embedded credentials and unsupported schemes are rejected. Blank `about:blank` child windows are allowed for popup authentication workflows.

Lite explicitly opens only `tel:`, `mailto:`, `sms:`, and `maps:`, after confirmation from a visible main-frame navigation. V2 allows WebKit to perform original web navigations. V1 cancelled some cross-domain links and issued new GET requests, which could lose referrer and user-activation context. V2 preserves native request semantics for links, forms, and popups. iOS can still apply Universal Link behavior to those flows: the installed SDK has no public navigation policy to prohibit every app-link handoff. Lite does not use the private policy value. [Apple documents Universal Link support in WKWebView](https://developer.apple.com/library/archive/documentation/General/Conceptual/AppSearch/UniversalLinks.html). App-specific custom-scheme deep links are rejected. Link previews are disabled to avoid implicit external navigation actions.

The UI provides back navigation, swipe history gestures, forward, reload, start page, share, bookmarks, saved downloads, loading progress, and dismiss. Offline/network/security failures have a retry screen. A terminated web process also presents a reload action instead of leaving a blank view. Download actions and main-frame attachment/unsupported responses use `WKDownload` in the originating profile. Progress and cancellation are visible. Completed files are retained in that profile's private Saved store, then previewed/shared or copied to Files with `UIDocumentPickerViewController` on request. Closing/locking a browser cancels unfinished transfers without deleting completed files. Export completion/cancellation preserves the saved original. Lite never transfers authenticated downloads into a shared URLSession or Safari.

JavaScript dialogs identify the requesting website. Each completion callback is consumed at most once. Closing a window, leaving the browser, or making the scene inactive cancels pending dialogs. Media pauses when the scene backgrounds. The app’s authentication wrapper hides inactive content and destroys a locked browser on backgrounding; persistent profile data remains intact.

## Content blocking

Before the first protected navigation, Lite compiles or loads a cached list derived from the bundled HaGeZi PRO mini snapshot. More than 53,000 domains are matched by host boundary, including subdomains and document loads. Native action/response policy checks use the same domain set for popup and redirect destinations. Conservative `css-display-none` rules hide explicit ad containers without blanket dialog removal. Resource rules work with JavaScript disabled. The rule grammar is restricted to [WebKit’s supported syntax](https://webkit.org/blog/3476/content-blockers-first-look/); alternation is not supported, so each domain has its own rule.

Shared compiled rules contain no cookies or browsing state. A content-derived cache identifier changes when the snapshot or rule format changes. If compilation fails while protection is enabled, the page does not load and the UI offers retry. Users can disable protection for an individual Lite App when a website breaks; enabling protection prepares rules first. List updates ship with app updates through `Tools/update_content_blocker.py`, which requires an immutable upstream revision and retains the original source data and license. The About screen names the list, its date and license. The app does not claim all first-party/video ads are blocked.

### Window approval and recovery

`createWebViewWith` returns a child built from WebKit’s supplied configuration, keeping the opener, profile and request semantics. Unapproved children are kept outside the visible page stack. Their navigation-policy completion is retained until Open/Dismiss, preserving original POST bodies. A separate child content controller temporarily blocks resource requests even for `document.write` content in an initial blank window. Approval removes the temporary rule; dismissal, navigation away, parent close and session close all resolve outstanding callbacks. One pending window and three approved children bound window storms.

Native controls show the destination, Open/Dismiss, an optional per-origin exception, Close popup and return, and Start Page. Source-origin exceptions are stored only within their container, can be revoked, and never override the ad blocker or WebKit’s automatic-window gate. A pending/background window cannot silently navigate the original page to another origin. Approved same-origin opener updates remain possible for authentication callbacks.

A session-only recovery entry records the previous committed GET page and its history item. Automatic redirect chains keep the earlier return destination. Recovery selects the old history item when available, otherwise reloads its URL as GET; POST results are not captured for replay. The observed redirect route (ignoring rotating query tokens) is blocked after recovery until deliberate link/form/history navigation. Native recovery is not an archive of form/DOM state. WebKit error 102 for policy/content-rule interruption does not replace retained website content with a generic failure overlay. Discover applies the same ad/recovery policy, but confirms new-window links as ordinary preview navigations rather than running account popup flows.

## Known compatibility limits

Session isolation cannot force a service to support embedded browsers. Some sites reject embedded sign-in, require their native app, or change their mobile website behavior. [Google’s OAuth policy](https://developers.google.com/identity/protocols/oauth2/policies#secure-browsers) restricts embedded user agents, so Google sign-in flows may be unavailable. Gmail and YouTube catalog entries are website shortcuts, not guarantees of account compatibility. Lite does not spoof Safari or bypass provider checks.

Device testing remains necessary for real provider logins, biometrics, media permissions, passkeys, file selection, and account persistence after a full process restart. Simulator cookie-isolation tests prove the profile boundary, but do not certify any third-party service’s current login flow.


## V2 integration audit

- `WKDownload`, download navigation policies and delegate methods: iOS 14.5+, verified in the installed public headers and [Apple documentation](https://developer.apple.com/documentation/webkit/wkdownload).
- `UIDocumentPickerViewController(forExporting:asCopy:)`: public export UI. File input uses WebKit's native picker; Lite does not read a file before selection.
- App Intents / AppEntity / AppShortcutsProvider: iOS 16+. `openAppWhenRun` brings Lite forward. The intent writes a one-shot app-ID request and posts an in-process notification, with launch/activation consumption as fallback.
- [OpenURLIntent](https://developer.apple.com/documentation/appintents/openurlintent) requires universal links, so Lite does not misuse it for a custom scheme. Widget links use the registered `lite://open/<UUID>` route. The parser rejects extra paths, queries, credentials, and ports.
- WidgetKit's iOS 17 container background and native Link/widgetURL routing are used. The App Group contains only launch metadata and a pending app ID, never URLs, cookie data or WebKit profile identifiers.
- The new coordinator and download owner use explicit nonisolated destructors to avoid the documented [Swift 6.2.4 back-deployment crash](https://github.com/swiftlang/swift/issues/88036) encountered on the iOS 26.2 simulator. They perform no actor-isolated cleanup in deinit; owners call explicit close/cancel methods.

No third-party browser dependency or copied upstream code was needed for this increment. All V2 implementation is local Swift/SwiftUI using public Apple APIs.

## Container controls (2.1)

`ContainerPreferences` applies `preferredContentMode`, `allowsContentJavaScript`, and `mediaTypesRequiringUserActionForPlayback` to configurations before constructing root and popup web views. `pageZoom` scales the actual web view. Preferences are snapshotted for each opening, avoiding partial configuration updates in an active session. User-created windows can be disabled; automatic popups remain disabled in either case. `WKUIDelegate` media-capture decisions return `.deny` for blocked hardware categories, closed/inactive sessions or nonactive pages, and `.prompt` otherwise. No `.grant` shortcut bypasses origin-specific WebKit consent.

`ContainerWebsiteData` queries `dataRecords(ofTypes:)` on the saved identified store. Removal uses either `removeData(ofTypes:modifiedSince:)` or the selected record with `removeData(ofTypes:for:)`. Cache removal excludes cookies, local/session storage and databases. UI operations await completion and refresh records. A per-profile cleanup barrier prevents a deep link from starting a page while its data is being cleared. These controls are accessible from the library, after the browser has closed; inspecting details does not create a web view.

`ContainerAccessView` shares the existing authentication/cover/relock behavior between browser and details. Additive SwiftData fields preserve V1/V2 identities and populated libraries. Recorded navigation diagnostics retain only a host, timestamps, connection observation, HTTP status, duration and error domain/code. Closed sessions cannot write late diagnostics. Nil represents unavailable/unobserved information; no fallback measurements are synthesized.

Public API references: [page preferences](https://developer.apple.com/documentation/webkit/wkwebpagepreferences), [page zoom](https://developer.apple.com/documentation/webkit/wkwebview/pagezoom), [media playback policy](https://developer.apple.com/documentation/webkit/wkwebviewconfiguration/mediatypesrequiringuseractionforplayback), [website data records](https://developer.apple.com/documentation/webkit/wkwebsitedatarecord), [website-data removal](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/removedata(oftypes:modifiedsince:completionhandler:)).

## Container proxy routing

`WKWebsiteDataStore.proxyConfigurations` (iOS 17+) receives one `Network.ProxyConfiguration(httpCONNECTProxy:tlsOptions:)` with `NWProtocolTLS.Options()` and `allowFailover = false`. No excluded domains are set. `WebProfileStore.configuredStore(for:)` validates the persisted configuration, retrieves credentials from the profile’s Keychain namespace, and applies routing before constructing the first WebView. Session route snapshots survive `release(identifier:)`; only process restart or actual profile removal permits a changed route. This deliberately avoids claiming that mutating a data store terminates established direct connections.

A failed setup creates only an empty nonpersistent view for the native error screen; `start()` and navigation policy deny loading. Popup configurations retain the same store. `WKDownload` stays in WebKit. Explicit icon refreshes use `URLSessionConfiguration.proxyConfigurations` with the same settings; failure never invokes the unproxied icon loader. Discover and initial creation remain separate.

Passwords are immutable Keychain records scoped to the profile UUID, with `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` and synchronization disabled. The model stores only a record UUID and connection settings. Saving a replacement password writes a fresh entry before saving SwiftData and removes it if the model save fails. Successful replacement cleans up the former entry; the durable profile-deletion workflow deletes all records for the profile. Duplicated containers require their own credentials and fail closed until configured. General preference reset preserves routing.

A controlled loopback test on iOS 26.2 showed that WebKit bypasses the proxy for localhost destinations. The UI discloses this limitation. The public API offers no complete per-profile VPN or DNS/WebRTC leak guarantee. HTTP CONNECT covers TCP, and the UI explicitly describes the limits. No private WebRTC switches, certificate overrides, JavaScript interception or Network Extension entitlements are used.

Verified against Xcode 26.3 / iOS 26.2 SDK declarations and Apple references: [WebKit proxy configurations](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/proxyconfigurations-cdc1), [HTTP CONNECT configuration](https://developer.apple.com/documentation/network/proxyconfiguration/init(httpconnectproxy:tlsoptions:)), [failover](https://developer.apple.com/documentation/network/proxyconfiguration/allowfailover), and [URLSession proxy configurations](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/proxyconfigurations).
